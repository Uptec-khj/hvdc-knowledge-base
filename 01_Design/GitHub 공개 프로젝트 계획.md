# GitHub 공개 프로젝트 계획

## 공개 목적과 v0.1 정의

HVDC 연구 방법과 근거를 다른 연구자가 탐색·검토하고 오류 수정과 후속 연구에 기여할 수 있도록 공개한다. GitHub에서는 일반 Markdown으로 읽고, Obsidian에서는 링크·속성·백링크를 이용한다.

v0.1은 **설계·템플릿·운영 기준의 공개 준비판**이다. 실제 논문 정독·근거 추출·종합 연구는 0건일 수 있으며, 그 경우 릴리스 설명과 README에 그대로 표시한다. RQ-001은 세부 주제가 확정되기 전까지 파일럿 제안이다.

## 공개 범위와 로컬 자료

| 구분 | 위치 | 기본 취급 |
|---|---|---|
| 연구 설계·직접 작성 요약·근거·비교·템플릿 | 기존 연구 폴더 | 검토 후 공개 |
| 공개 운영 이력 | `80_Operations` | 개인정보·개인 경로·계정 정보를 적지 않음 |
| 개인 연구 메모·백업 위치·비공개 실험 | `Private` | Git 추적 제외 |
| 원문·원본 그림·표준·실험 데이터 | `95_Attachments`의 안내 외 파일 | Git 추적 제외 |
| 공개 조건을 확인한 그림·데이터 | `assets` | 출처·권리자·라이선스 또는 이용 조건 등록 후 공개 |
| Obsidian 개인 설정·플러그인 설정 | `.obsidian` | Git 추적 제외 |

공개 노트에는 외부 원문의 DOI·발행처 URL을 우선 넣는다. 개인 PDF 경로는 `Private`의 메모에서 관리한다. 공개 페이지가 로컬 전용 파일에 의존하지 않게 한다. `10_Inbox`, `80_Operations`, `99_Archive`는 공개 대상이므로 비공개 내용의 보관 장소로 사용하지 않는다.

## 라이선스 결정 게이트

후보는 CC BY 4.0, CC BY-SA 4.0, 결정 보류다. 라이선스는 아직 적용하지 않는다.

| 후보 | 판단 질문 | 공개 영향 |
|---|---|---|
| CC BY 4.0 | 출처·변경 표시를 전제로 폭넓은 재사용을 허용할 것인가? | 수정물의 동일 라이선스 적용 의무 없음 |
| CC BY-SA 4.0 | 공개 수정물에도 동일조건 공유를 요구할 것인가? | 동일조건 공유 요구가 있음 |
| 결정 보류 | 지금 재사용 조건을 확정할 수 없는가? | 공개 업로드·릴리스 보류, 로컬 준비만 진행 |

선택 후 직접 작성한 문서·템플릿에 적용되는 범위를 README에 명시한다. 외부 논문·표준·그림·데이터는 해당 라이선스에 포함되지 않음을 구분한다. 코드가 추가되면 코드 라이선스를 별도로 결정한다.

## 공개 릴리스 로드맵

| 단계 | 연구 로드맵 연결 | 공개 산출물 | 완료 기준 |
|---|---|---|---|
| v0.1 계획 | 연구 시작 전 또는 1주차 범위 결정 후 | 설계·로드맵·템플릿·제안 질문 | 공개 P0 게이트 통과, 실제 연구 수치와 미결정 사항 표시 |
| v0.2 계획 | 4주차 G1 | 파일럿 문헌·근거·첫 종합 | G1 실제 통과, 각 결론의 원문 위치·범위 확인 |
| v0.3 계획 | 8주차 G2 | 비교 확장·상충 근거·동향 | 재현 가능성·한계·변경 이력 기록 |
| v1.0 계획 | 12주차 G3 | 첫 연구 묶음 | 해당 질문 범위의 근거 추적·후속 질문 완료 또는 미달 공개 |

버전은 향후 제안이며 실제 태그나 릴리스가 아니다. v1.0도 HVDC 전 분야의 완전한 지식이나 기술 검증 완료를 의미하지 않는다.

## v0.1 공개 게이트

필수 검사는 [공개 전 점검표](../PUBLICATION_CHECKLIST.md)를 단일 기준으로 사용한다. 특히 라이선스 결정, 공개 파일 인벤토리, 민감정보·권리 점검, 상태·성과 수치 검증, 링크 무결성, 저장소 식별자 확정이 끝나기 전에는 실제 공개 작업을 하지 않는다.

## 첫 업로드 절차

1. 저장소 소유자·이름·기본 브랜치·공개 라이선스를 확정한다.
2. 공개 후보 사본에서 추적 대상과 제외 대상을 검사한다.
3. Git dry run으로 첫 커밋 예상 목록을 검토한다.
4. P0 게이트를 모두 통과한 뒤에만 Git 저장소를 초기화한다.
5. 공개 GitHub 저장소를 생성하고 원격 주소를 연결해 업로드한다.
6. GitHub에서 README, 대표 링크, Mermaid, Issue/PR 양식을 확인한다.
7. clean clone을 Obsidian으로 열어 템플릿과 탐색 경로를 확인한다.
8. 실제 수치·알려진 한계·라이선스 범위를 포함한 v0.1 릴리스 설명을 게시한다.

제외 규칙은 초기 커밋 전에 적용한다. 이미 기록된 파일의 제거·이력 수정은 별도 작업이며 공개 이력에 민감자료가 들어갔다면 단순 삭제만으로 끝내지 않는다. 개인 데이터 백업은 GitHub 공개 저장소와 별도로 운영한다.

## 기여 운영

관리자는 문서의 출처·상태·라이선스 적합성을 검토하고 PR을 병합한다. 개인 운영자 1인 단계에서는 별도 검토자가 없으므로 체크리스트와 커밋 설명을 검토 기록으로 쓴다. Issue는 문헌 제안·오류 수정·연구 질문 제안에 사용한다. 연구 내용과 폴더 구조 변경을 한 PR에 크게 섞지 않는다.
